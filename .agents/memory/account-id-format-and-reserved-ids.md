# Account ID (`NCB-...`) — durable decisions

`account_id` is a STORED generated column off the `account_seq` identity column.
Format is `'NCB-' || lpad(account_seq, N, '0')`; current width N = 10.

## GOTCHA: `drizzle-kit push` silently ignores generated-column expression changes
Editing the `lpad(...)` expression in the schema and running push prints
"Changes applied" but **leaves the old expression in the DB**. Do not trust the
success message — verify with a real query. To change the format you must ALTER
the column by hand (drop + re-add the generated column); it has no FK/index/unique
dependents, so re-adding safely recomputes every row. Prod picks up the new
format from the dev-schema snapshot on the next publish.

## Reserved-ID layout (a product decision, enforced by the startup seed)
- seq 1 = superadmin, seq 2 = intentionally unassigned, seq 3 = demo; real
  accounts start at seq 4 (`NCB-0000000004`).
- **Why enforced in the seed, not the DB:** prod is schema-only on publish (empty
  users table) and reseeded on boot, so the layout has to be reproducible from the
  seed alone. Reserved accounts are inserted with explicit `account_seq`.

## Why the sequence floor must be MONOTONIC (never lower it)
Explicit inserts into a GENERATED BY DEFAULT identity do NOT advance its sequence,
so the seed bumps the floor to at least MAX(seq)+1 (≥4). But it must ALSO floor at
the sequence's own current value and never go below it.
**Why:** accounts can be deleted (ARCO "eliminar cuenta"). If you floor only to
MAX(account_seq) and the highest-seq account was deleted, the next new account
reuses that seq — and thus its permanent NCB id. `account_id` must never be
reused. A setval that can lower the sequence is the bug; guard with GREATEST over
the sequence's current position.
